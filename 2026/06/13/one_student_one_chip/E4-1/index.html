实际上不可能报告所有的警告

  1. 编译器的极限：-Wall 在 GCC/Clang 中并不是真正意义上的“所有警告”，而是一组常用、合理的警告集合。它的命名有历史原因——早期 GCC 的 -Wall 确实试图包含“所有”警告，但随着 C 语言标准的演进和编译器优化，很多潜在的深层问题（如未初始化变量、类型不匹配、未使用函数等）被划入了 -Wextra、-Wpedantic、-Wconversion 或其他更高级的选项组，而不是 -Wall 中。

  2. 语言本身的不确定性：C 语言允许一些合法但危险的写法（例如隐式类型转换、指针别名问题），编译器无法在编译时静态地检测所有可能的运行时错误（如缓冲区溢出、并发问题）。即使打开所有已知的警告选项，也无法覆盖这些动态或语义上的缺陷。

字符 % 后面可以跟零个或多个以下标志：

#
值将被转换成“替代形式”。

  • 对于 o 转换，输出字符串的第一个字符变为零（如果原来不是零，则在其前面加上一个 0）。
  • 对于 x 和 X 转换，如果结果非零，则在其前面加上 "0x"（或 "0X"，对应 X 转换）。
  • 对于 a、A、e、E、f、F、g、G 转换，结果中始终包含一个小数点，即使后面没有数字（通常情况下，这些转换只有当小数点后有数字时才显示小数点）。
  • 对于 g 和 G 转换，结果中的末尾零不会被移除（否则默认会移除）。
  • 对于其他转换，行为未定义。

%#g 123.0 123.000 保留末尾的零（默认 %g 会去掉末尾零）

0

如果同时指定了 0 和 - 标志，则忽略 0 标志。如果给定了数值转换（d、i、o、u、x、X）的精度，则忽略 0 标志。对于其他转换，行为未定义。

这一节，对我来说比较新颖的是 这个 原型继承，别的就略过了

传统基于类的继承（如 Java、C++）

  • 源是 类（一个抽象模板/蓝图）
  • 对象是类的实例化结果
  • 继承关系是 类继承类（比如“猫类”继承“动物类”）
  • 你无法直接拿一个具体的猫对象去当作其他猫的模板

原型继承（如 JavaScript）

  • 源是 一个具体的对象（比如你创建了一个叫 myProto 的对象，里面有方法 sayName）
  • 新对象通过 Object.create(myProto) 或设置 __proto__ 来链接到这个具体对象
  • 本质上就是：“我想创建一个新对象，它应该像那个现有对象一样工作，但还能加上自己的东西”

在典型的原型继承系统中（比如 JavaScript），原对象被修改后，所有通过该原型创建的对象都会立即受到影响——只要这些对象自己没有覆盖该属性。

这就是所谓的原型共享。但是，这也取决于具体实现。有些“原型风格”系统可能采用克隆方式。

proto 表示 原型 prototype

struct 的 -> 和 .，通过基地址 + 编译期已知的偏移量，再将结果解释为指向成员类型的指针，从而读取或写入该成员。

代码中的 object.describe 函数不管你是啥，直接当作 void，再转换为 object，直接按照 object* 方式读取。只要你是 将 object 放在 类的开头，就自然满足。

scanf 并不会“报错”（即程序不会因为输入不匹配而崩溃或产生错误信息），而是匹配失败，并返回一个小于预期的返回值。否则，返回匹配成功的个数。

其实无论什么情况返回的都是匹配的个数。开头就没匹配上，那就是匹配了 0 个，所以返回 0。匹配了一半没匹配上那就返回匹配上的那几个个数。

  • 如果输入是 "xxx123xxx"，那么匹配成功，ret 返回 1（成功读入 1 个整数），x 被赋值为 123。
  • 如果输入是 "123"（缺少开头的 "xxx"），则第一个字符 '1' 与格式要求的 'x' 不匹配，scanf 立即停止读取，返回 0，x 不会被赋值（它保留原有值，可能是未初始化的垃圾值）。
  • 如果输入是 "xxx123"（缺少结尾的 "xxx"），那么前三个 'x' 匹配，读入整数 123，然后期待下一个字符是 'x'，但实际可能是回车或结束，这时 scanf 停止，并返回 1（因为成功读入了整数），但后续的 "xxx" 没有匹配完，输入流中剩余的字符会被留下。

/dev/urandom 是 Linux/Unix 系统中的一个字符设备文件，用于提供伪随机数生成器（PRNG） 的输出。对于这个实验来说，你并不知道什么时候才会有换行符，所以很有可能会导致缓冲区溢出暴毙。

  • last 是函数参数列表中最后一个固定参数（即最后一个有名有类型的参数）的名称。va_start 通过 last 参数的地址来计算后续可变参数的位置。例如：
    va_arg是一种宏，展开为一个表达式，该表达式具有 va_list 中下一个参数的类型和值。

  • 每次调用 va_start() 必须由同一函数中对应的 va_end() 调用与之匹配。
  • 在调用 va_end(ap) 之后，变量 ap 是未定义的。

va_arg(ap, char) 会产生警告：

  • C 语言标准（C99 / C11 / C17）明确要求：对于可变参数列表中的参数，会发生默认参数提升（default argument promotions）。具体规则是：
    • 所有 char、short、unsigned char、unsigned short 类型的参数会被转换为 int（如果 int 能表示所有值；否则转换为 unsigned int）。
    • 所有 float 类型的参数会被转换为 double。
      为什么要提升？
      主要是历史原因和调用约定的简化。在早期的 C 语言和许多处理器架构中，函数的参数都通过栈传递，栈一般是按字（word）对齐的（例如 16位、32位、64位）。直接传递 char 或 short 会破坏对齐，并且处理不同类型的长度会显著增加编译器复杂度。因此设计者决定：让可变参数部分统一使用 int 和 double 这些 “自然长度” 的类型，从而简化了 va_list 的实现和参数遍历。

链接器的库搜索顺序是严格的从左到右。当链接器处理输入文件时，如果库出现在需要引用它的目标文件之前，链接器会认为该库的符号暂时没有被使用，从而跳过它，不会将其标记为已解析。等到后面遇到引用这些符号的目标文件时，链接器不会回头再去看之前的库，因此报告“未定义引用”。
在你的原始 Makefile 中，链接命令是：
cc ... -L/usr/local/apr/lib -lapr-1 -pthread -laprutil-1 devpkg.c ... -o devpkg
库 -lapr-1 等出现在所有 .c/.o 文件之前，这导致链接器先看到库，但由于此时尚未有目标文件引用其中的符号，链接器直接跳过；当它处理后面的目标文件时，遇到了 apr_pool_initialize 等符号引用，却无法再解析，因此报错。
将库分离到 LDLIBS 中，并在链接命令中显式将库放在所有目标文件之后：
$(CC) $(CFLAGS) $^ $(LDFLAGS) $(LDLIBS) -o $@
这里 $^ 是目标文件列表（先出现），$(LDLIBS) 在最后，保证了链接器先扫描所有目标文件，建立未解析符号列表，再处理库，从而能够正确解析这些符号。这就是分离后能解决问题的根本原因。
在 GNU Make 的隐式规则中，默认链接命令是 $(CC) $(LDFLAGS) ...，而 LDLIBS 通常被最后附加，所以将库放入 LDLIBS 是符合标准的做法。

技巧

  1. gdb --args：通常 gdb 会认为你传递给它的所有参数都是自己的参数。而使用 --args 选项后，后续的参数会被当作被调试程序的参数传递给它。例如：
    gdb --args ./myprogram arg1 arg2
    这样启动 GDB 后，被调试的程序会收到 arg1 和 arg2 作为命令行参数。
  2. **thread apply all bt**：打印所有线程的执行轨迹（调用栈）。当调试多线程程序时，这个命令能一次性显示每个线程当前正在执行的函数调用链，非常有助于分析死锁、多线程异常等问题。
  3. **gdb --batch --ex r --ex bt --ex q --args**：这是一个无交互模式下的自动化调试命令。含义如下：
    • --batch：以批处理模式运行，不进入交互界面。
    • --ex r：执行 run 命令，启动程序。
    • --ex bt：程序停止后（如崩溃）执行 backtrace（打印调用栈）。
    • --ex q：执行 quit，退出 GDB。
    • --args：后续参数传递给被调试程序。
      整体作用：让程序运行，一旦崩溃就打印调用栈并退出，适合脚本化分析程序崩溃原因。

核心转储

core dump（核心转储文件） 包括

  • 程序的内存映像：所有已分配的内存（堆、栈、数据段、代码段）的完整内容，例如变量值、动态分配的数据、函数调用栈等。
  • 寄存器状态：CPU 各寄存器（如程序计数器、栈指针、通用寄存器）的当前值，用于精确还原执行位置。
  • 进程控制信息：进程 ID、信号处理状态、打开的文件描述符等。

核心转储打开方式：
ulimit -c unlimited 在当前会话 解除限制

输出是 |/usr/share/apport/apport ...（Ubuntu 常见），表示 core dump 被 Apport 拦截处理，文件会存放在 /var/lib/apport/coredump/ 目录下。

打开格式：gdb <可执行文件> <core文件>
