git

基础

  • git add 精确地将内容添加到下一次提交中
  • git commit 提交一次快照
    • -a 可以跳过暂存，直接提交
    • –amend 如果提交后发现有文件忘记提交，该参数会将暂存区中的文件提交。 如果自上次提交以来你还未做任何修改（例如，在上次提交后马上执行了此命令）， 那么快照会保持不变，而你所修改的只是提交信息。最终你只会有一个提交——第二次提交将代替第一次提交的结果。

      与其说是修复旧提交，倒不如说是完全用一个 新的提交 替换旧的提交

  • git diff 工作目录中当前文件和暂存区域快照之间的差异【 本身只显示尚未暂存的改动，而不是自上次提交以来所做的所有改动】
    • git diff –staged/cached 比对已暂存文件与最后一次提交的文件差异
    • git diff --check，它将会找到可能的空白错误并将它们为你列出来
  • git rm 从暂存区域移除，并连带从工作目录中删除指定的文件，然后提交
    • 如果某个文件是新文件&在它第一次被添加到 暂存区后，或者有过提交但是现在本地有改动，git rm 是没法直接删除的，因为这样删除会将源文件或为保存的修改一并删除。所以为了放置误删，需要添加 -f force 参数。
    • 如果你仅是想让文件不被跟踪，而不是删除，那么添加 --cache 即可。
    • 不过如果你是先删除的文件，再删除的暂存区，那是没有任何冲突的，如：
  • git mv 移动文件，相当于：
  • git log
    • –stat 统计信息
    • –graph 图形显示
    • --pretty= oneline、short、full、fuller、format（format格式见这里）
    • 其它常用参数也见这里
  • 取消暂存的文件，这个在 git status 里面会提示你
  • git clone 克隆远程仓库
  • git remote 远程仓库，列出你指定的每一个远程服务器的简写
    • -v 显示需要读写远程仓库使用的 Git 保存的简写与其对应的 URL
    •  git remote add <shortname> <url> 添加远程仓库
    •  git remote rename 来修改一个远程仓库的简写名
    • git remote remove 或 git remote rm 移除一个远程仓库
  • git getch <remote>访问远程仓库，从中拉取所有你还没有的数据。
  • 打标签略，见[这里](Git - 打标签)

分支

建议参考[这里](Git - 分支简介)，讲的很清楚
 Git 的分支实质上仅是包含所指对象校验和（长度为 40 的 SHA-1 值字符串）的文件，所以它的创建和销毁都异常高效（其实你可以在 .git 中找到）

  • git branch，仅跟分支相关，如创建、列出现有分支等等
    • 不加参数，列出分支
    • 添加 名称，创建需要创建的分支
    • 添加 -d 再名称，删除指定分支
    • git branch -v 查看每一个分支的最后一次提交
    • git branch --merged 查看哪些分支已经合并到当前分支 
    • git branch --no-merged 查看所有包含未合并工作的分支
    • git branch 的 -vv –verbose –verbose 的缩写，意为双重详细模式。它显示每个本地分支的最新提交哈希、提交信息，以及该分支所跟踪的远程分支（如果有）
  • git checkout， 分支切换
  • git merge <branch>，将当前分支，合并到指定的 branch
  • git fetch fetch 下载远程分支的新提交并更新对应的远程跟踪分支指针，但完全不改动你的工作目录和当前本地分支，只是保存了一个独立的快照。【由于没有切换或合并分支，所以此时你看不到冲突。只有在 merge 的时候，你才会碰到冲突。】
  • git pull <branch>，将当前分支，合并到指定的 branch
    • 其实就是一个 git fetch 紧接着一个 git merge 命令
  • git rebase branch(或某个commit) 提取其它分支上的补丁和修改，在当前的commit上，再应用一次，即为 rebase 变基。

三方合并：Git 会进行两次差异比较：

  • 从 Base 到 Ours 的变更（我们的修改）
  • 从 Base 到 Theirs 的变更（对方的修改）
  • 然后，Git 尝试将这两组变更同时应用到 Base 上，产生合并结果。

远程分支

  •  git ls-remote <remote> 来显式地获得远程引用的完整列表
  •  git remote show <remote> 获得远程分支的更多信息
  • 远程跟踪分支是远程分支状态的引用。它们是你无法移动的本地引用。 <remote>/<branch>，就是远程分支所在位置。一旦你进行了网络通信， Git 就会为你移动它们以精确反映远程仓库的状态。比如这里：
  • git fetch 抓取并移动
  • git push <remote> <branch>  会将本地的 <branch> 分支（而非当前分支）推送到远程同名的分支。即使当前处于其他分支。
    • git push -u <remote> <local_branch>:<remote_branch> --set-upstream（或其简写 -u）是 git push 的一个选项，用于建立本地分支与远程分支的关联关系。当你第一次推送一个新分支时，加上 --set-upstream 后，Git 会记住”这个本地分支对应远程的哪个分支”。以后你只需要输入 git push 或 git pull，Git 就会自动知道往哪里推送/从哪里拉取，无需再写完整的远程和分支名。
    • 删除远程分支：
        • git push <remote> --delete <branch>
      • git push <remote> :<branch>
        `git push <remote> <src>:<dst>` 的语法中，`<src>` 表示本地分支或引用的名称，`<dst>` 表示远程分支的名称。当 `<src>` 为空（即冒号前面不写任何内容）时，相当于推送一个空引用到远程，从而删除远程上对应的 `<dst>` 分支
    \**这种写法可以将本地分支A提交到远程分支B，即 `git push <remote> A:B`*。

拉取请求

*注意，这是 你请求别人拉去你的仓库，合并你的工作

  • git request-pull <目标分支> <源仓库URL或别名> [<源分支>]

添加补丁

  • git apply /tmp/patch-ruby-client.patch
  • git apply –check 0001-seeing-if-this-helps-the-gem.patch 检查补丁是否可以顺利应用
  • git am 用于接受  format-patch 生成的补丁

跟踪分支

从一个远程跟踪分支检出一个本地分支会自动创建所谓的“跟踪分支”（它跟踪的分支叫做“上游分支”）。 跟踪分支是与远程分支有直接关系的本地分支。 如果在一个跟踪分支上输入 git pull，Git 能自动地识别去哪个服务器上抓取、合并到哪个分支。

克隆一个仓库时，它通常会自动地创建一个跟踪 origin/master 的 master 分支

不过注意：只对尚未推送的本地提交进行 rebase（即 fetch 之后本地新产生的提交），而不要去 rebase 已经推送到远程的提交（那些已经被别人共享的 commit）。这样既能保持本地历史的简洁，又不会干扰他人的工作，避免 force push 带来的混乱。

  • git show 用于显示某个 Git 对象的详细信息。
  • git blame 用于逐行追溯文件中每一行的最后修改者（提交和作者）。执行 git blame <file> 会输出每一行最右侧的版本，左侧显示该行最后一次被修改的提交哈希、作者、时间

  2. 从 GitHub 上克隆某个仓库，修改一些文件。当您使用 git stash 会发生什么？当您执行 git log --all --oneline 时会显示什么？通过 git stash pop 命令来撤销 git stash 操作，什么时候会用到这一技巧？

  • 在 dirty 的情况下，如果想要 pull 仓库，建议:
      1. commit 现有的修改
      1. 如果你觉得当前的工作并不达到 commit，可以 stash 暂存
  • 当你希望记录工作目录和暂存区的当前状态，但又想恢复到干净的工作目录时，可以使用 git stash。该命令会保存你的本地修改，并将工作目录还原到与 HEAD 提交一致的状态。
  • 通过该命令暂存的修改可以通过 git stash list 列出，通过 git stash show 查看，并通过 git stash apply 恢复（可能应用于不同的提交之上）。不带任何参数调用 git stash 等同于 git stash push。默认情况下，贮藏会以 “WIP on branchname …” 的形式列出，但你可以在创建时在命令行中提供更具描述性的消息。
  • 你创建的最新贮藏存储在 refs/stash 中；较旧的贮藏可在该引用的 reflog 中找到，并可通过常规的 reflog 语法命名（例如，stash@{0} 是最近创建的贮藏，stash@{1} 是之前的贮藏，stash@{2.hours.ago} 也是可行的）。此外，仅指定贮藏索引即可引用贮藏（例如，整数 n 等同于 stash@{n}）。
  • git stash  并不是仅保存差异（diff），而是创建一个完整的快照（类似于一个提交对象），它记录了当前工作目录和暂存区中所有被修改或暂存的文件的完整内容。
    • 当你执行 git stash 时，Git 会基于当前 HEAD 提交（记为 c1）构建一个新的树对象，该树对象包含了当前工作目录和暂存区中所有已修改、已添加、已删除的文件内容。未修改的文件则直接引用 c1 中的相同对象，不会重复存储。
    • 然后 Git 创建一个新的提交（通常称为“WIP”提交），它的父提交是 c1，树对象就是上面构建的树。这个提交实际上就是一个完整的文件系统快照（只包含与 c1 不同的部分，但由于 Git 的对象模型，相同内容只存一次，所以本质上是对整个工作树的状态进行了保存）。
    • 之后，Git 会将工作目录和暂存区恢复到 c1 的状态（即干净的工作区）。
  • 当在其它分支上进行 git stash apply 的时候，其实类似于 git merge。本质上是进行了一次三向合并
    • 当你执行 git stash apply 时，Git 会进行如下操作：
      1. 确定共同祖先：存储（stash）的父提交是创建该存储时的 HEAD（记为 base）。
      2. 确定两份差异：
        • 存储相对于 base 的更改（即你当时暂存的修改）。
        • 当前 HEAD 相对于 base 的更改（即从创建存储到当前所经历的所有提交）。
      3. 三向合并：Git 尝试将这两份更改应用到 base 上，就像执行 git merge 一样——它会找出冲突并尝试自动合并。如果没有冲突，则直接应用；如果有冲突，则会在工作区留下冲突标记，需要手动解决。
    • 因此，如果在不同的分支或更靠后的提交上恢复存储，这个合并过程会考虑当前分支上的所有变更，并根据共同祖先进行合并。这与 git merge 的核心机制完全相同，区别仅在于：
      • git merge 会创建一个新的合并提交。
      • git stash apply 不会产生任何提交，仅修改工作树和暂存区（可能还会留下冲突标记）。
  • git stash 的存储顺序是基于 refs/stash 引用对应的 reflog 来管理的。
    • stash@{0}：始终指向最近一次创建的贮藏（最新的 stash）。
    • **stash@{1}**：指向次新创建的贮藏（即 stash@{0} 之前的那一次）。
    • 以此类推，stash@{n} 表示第 n+1 新的贮藏（时间上更早）。
  • git stash 模型其实类似于一个栈。这也和上一条，为什么 0 可以一直指向最新的实现上做了解释
    • git stash push 这里的 push 表示的是压栈，而不是提交
      • 而 git stash，其实就是 git stash push 的简写
    • git stash pop 表示弹出
      • 可以将 pop 理解为“应用并弹出”，而 apply 只是“应用”。如果你的意图是应用一次后不再需要该贮藏，用 pop 更方便；如果希望保留以备后用，则用 apply。
      • 等价于：
        • git stash apply stash@{x}
        • git stash drop stash@{x}【*不过 对于 pop，drop 仅发生在 apply成功且没有冲突的时候。否则仍会保留 stash】
  • git stash 默认设计认为未跟踪文件不是当前工作进度必要组成部分，因此不自动包含，以避免不必要的存储与复杂度
  • 本题目的其它小问题回答：
    - 执行 git log --all --oneline 就是每个提交仅显示第一行，并列出全部的提交
    - git stash pop 对于很多快速恢复，并不需要重新多次应用的时候非常好用

  1. 与其他的命令行工具一样，Git 也提供了一个名为 ~/.gitconfig 配置文件 (或 dotfile)。请在 ~/.gitconfig 中创建一个别名，使您在运行 git graph 时，您可以得到 git log --all --graph --decorate --oneline 的输出结果；

  2. 您可以通过执行 git config --global core.excludesfile ~/.gitignore_global 来设置全局忽略文件的位置，这会告诉 Git 使用该文件，但您仍需要手动在该路径创建 ~/.gitignore_global 文件。配置您的全局 gitignore 文件来自动忽略系统或编辑器的临时文件，例如 .DS_Store；

  • core.excludesfile 指定的文件，只有唯一一个功能：提供忽略规则。
