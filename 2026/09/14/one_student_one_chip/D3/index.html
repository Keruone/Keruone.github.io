AM 结构

AM 屏蔽的是“硬件平台差异”，向上提供一套统一的抽象接口，让操作系统和应用程序不必直接面对具体硬件。

AM根据程序的需求把库划分成以下模块

  • TRM(Turing Machine) - 图灵机, 最简单的运行时环境, 为程序提供基本的计算能力
  • IOE(I/O Extension) - 输入输出扩展, 为程序提供输出输入的能力
  • CTE(Context Extension) - 上下文扩展, 为程序提供上下文管理的能力
  • VME(Virtual Memory Extension) - 虚存扩展, 为程序提供虚存管理的能力
  • MPE(Multi-Processor Extension) - 多处理器扩展, 为程序提供多处理器通信的能力 (MPE超出了ICS课程的范围, 在PA中不会涉及)

Makefile 详解

  • 将 Makefile 首行除了注释之外都添加4个空格，然后转换为 html
    • sed 用来捕获首行开头（^）不是#（[^#]）的行

Make 前检查

  • 先设置默认目标为 image
    • image 是 makefile 的一个 目标
    • ifeq(A, B) 会比较 A B 是否一致
  • 如果 当前的 MAKECMDGOALS 没有 clean 之类的别的目标，则
    1. 输出构建信息
    2. 检查 AM_HOME 下相关文件是否存在，不存在则报错
      • 使用 wildcard 匹配，如果匹配上就会输出。使用这个特性完成
    3. 获取全部的 ARCHS，然后查看要求的 ARCH 是否在其中，不存在则报错
    4. 分离 ARCH 中的 ISA 和平台，如 ARCH=x86_64-qemu -> ISA=x86_64; PLATFORM=qemu
      • $(subst, from, to, text) 会将 text 中 from 的部分 替换为 to 的部分
    5. 检查 是否已经定义 SRC，否则报错
      • flavor 函数是 GNU Make 提供的一个文本处理函数，它的作用是获取一个变量的 “风味”（flavor），即判断一个变量是如何定义的。在 Make 中，变量主要有两种“风味”
        • recursive（递归展开型）使用 = 或 define 定义的变量。这类变量的值会在使用时才展开，如果其值中包含对其他变量的引用，这些引用也会被递归地展开。
        • simple（简单展开型）使用 := 或 override ... := 定义的变量。这类变量的值在定义时就被立即展开，展开结果是固定的字符串。

Make 配置 设定

  • 设置工作目录、目标目录，并创建
  • 设置编译目标的 相对路径、绝对路径、静态库路径
  • 设置 编译目标、调用链接、链接的输入列表
    • 编译汇编后得到的机器码文件。通过提取 basename，然后添加前后缀设定 .o 目标文件的绝对路径
    • 库文件 默认有 am klib（这俩目前还是字符串），还有展开的 LIBS。使用 sort 去重。
      • 如果用 =（递归展开），会导致无限递归。因为右边引用了 LIBS 自己。用 = 的话，每次展开 LIBS 都会再去展开右边的 LIBS，形成循环。用 := 就先把当前值算出来，再赋回去，避免了这个问题。
    • 链接输入列表就使用 $(OBJS)

      这可能即作为某个完整编译过程中的生成文件，也作为某一步骤的源文件。

编译 配置

  • 设置编译配置
  • 添加头文件路径
    • 工作路径 的 include
    • AM_HOME 添加后缀 /include/
    • 使用 addprefix，给每个元素添加 -I前缀
  • 设置架构的头文件
  • 设置编译参数
  • 设置 cxx(c++)选项、汇编选项、连接选项
选项 含义
-O2 开启二级优化
-MMD 生成 .d 依赖文件，让 Make 能追踪头文件变化
-Wall 开启常用警告
-Werror 把警告当错误，强制代码干净
$(INCFLAGS) 包含路径（-I...）
-D 宏定义
选项 作用 为什么要关
-fno-asynchronous-unwind-tables 不生成异步 unwind 表 裸机环境不需要异常展开信息，省空间
-fno-builtin 不把 printf 等识别为内建函数 避免编译器优化掉你自定义的实现
-fno-stack-protector 关闭栈保护 裸机没有对应的运行时支持
选项 作用
-Wno-main 不警告 main 的签名问题（裸机里 main 可能不标准）
-U_FORTIFY_SOURCE 取消 _FORTIFY_SOURCE 宏，避免依赖 libc 的检查
-fvisibility=hidden 默认符号不可见，减少符号冲突

架构对应配置

以 ARCH 为 riscv32-nemu.mk 为例

  • isa 使用 riscv 的
  • platform 使用 nemu 模拟硬件
  • gcc 编译添加 宏定义 ISA_H 为 “riscv/riscv.h”
  • COMMON_CFLAGS：这些选项不只给 C 用，C++、汇编等阶段也可能需要。
    • -march=rv32im_zicsr 指定生成 RV32IM + CSR 扩展的 RISC-V 指令，-mabi=ilp32 指定 32 位整数/长整型/指针的调用约定；注释 # overwrite 表示这是有意覆盖之前的设置，确保整个构建统一到这套目标上。
  • 链接 flag
  • AM 用来处理 riscv 的相关源文件。
    • 在 $AM_HOME/am/src/riscv/nemu/

编译规则

1. 对于单个文件

  • $@ 表示 target，$<表示第一个依赖，$^ 表示全部依赖

2. 打包

  • 如果 目标是 archive，那就打包
  • 如果当前 make 的目标不是 archive，那么对 LIBS 里的每个库，生成一条“递归进入该库目录执行 make archive”的规则，并把生成的 .a 加入 LINKAGE。在 foreach 展开 LIBS，依次调用
    • $(foreach 变量名, 列表, 表达式)
    • $(eval 文本) 会把“文本”解析成 Makefile 语法，并立即生效。
      • $(1) 表示 call 第一个参数 $(call 模板, 参数1, 参数2, 参数3)
    • 注意，$$(AM_HOME)/$(1)/build/$(1)-$$(ARCH).a: force 是在模仿 Makefile 的语法，前面是 target。
    • 这里force 后文能看到这个 target，什么 dependence 都没有，仅仅作为强制这个命令必须执行罢了
    • $$ 不是“两个美元符号”，而是**一个转义后的 $**。
写法 展开时机 为什么
$(1) call 时立即展开 参数必须在调用时确定
$$(AM_HOME) eval 时展开 路径要等规则真正生效时才确定
$$(ARCH) eval 时展开 体系结构要等 eval 时确定
$$(MAKE) eval 时展开 让子 make 使用正确的 make 变量

3. 创建 image.elf

  • $(LINKAGE)：之前收集的所有 .o 和依赖库 .a
  • $(LDSCRIPTS)：链接脚本，决定内存布局
  • 如果当前 arch 中有 native 字样
    • 使用 C++ 编译器做链接
  • 否则使用 连接器链接
    上面生成的都是 .elf 的二进制文件，还不算完全的镜像。

4. 添加依赖

  • Makefile 通过 gcc 的 -MMD 生成 .d 依赖文件，再用 -include 读入，让 Make 知道每个 .o 依赖哪些 .h，从而在头文件改动时自动重新编译。
  • -include 是 Make 的指令，由 Make 解析 Makefile 时读取 .d 依赖文件并当作规则；.d 则由 gcc 的 -MMD 在编译时生成。
  • -MMD 生成的 .d 文件就是 Makefile 格式的依赖规则，Make 用 -include 读入后直接当作普通规则使用。

杂项

  • image 不直接依赖 .elf，而是通过 image-dep 中转。这样设计通常是为了让“构建镜像”和“准备依赖”分成两个阶段，方便控制。
  • force 用作给别的作依赖，然后强制那个 target 执行一次
  • clean-all 先用 find 找出所有子项目的 Makefile 目录，逐个进入执行 make clean（忽略错误），最后再清理当前项目。

[!bug] vim coc 没有办法正确跳转，并且语法检查报错

现象：编译运行完全正常（GCC 支持 zicsr），但 vim 中没有办法跳转到头文件定义，且报错提示 Invalid arch name 'rv32im_zicsr' 和“未找到 ‘klib’ 的任何定义”。

原因：

  • 工具链脱节：PA 实际编译用的是 GNU 交叉编译器（riscv64-linux-gnu-gcc），它认识 zicsr 扩展；而 vim 的语法检查（coc.nvim 调用的 clangd 语言服务器）底层是旧版 Clang（如 14），它不认识 zicsr 参数，直接抛出架构错误。
  • 路径解析缺失：clangd 默认不会主动读取 Makefile 的构建逻辑，需要读取 compile_commands.json 才能获取正确的 -I 头文件搜索路径，否则无法定位 klib.h 等头文件。

解决：在 cpu-tests/ 目录下执行 bear -- make ARCH=riscv32-nemu ALL=string run。然后移动到项目根文件夹即可。（注：bear 会生成 compile_commands.json，clangd 读取后便能正确识别头文件路径和架构参数）。

[!bug] 编辑器与工具链的奇怪报错
现象：编译运行完全正常（GCC 支持 zicsr），但 VSCode 里提示“未找到 klib 定义”，且没有红波浪线。

原因：VSCode 使用的 C/C++ 插件或旧版 clangd 没有正确读取 compile_commands.json，导致无法解析头文件路径。

解决：升级系统 Clang 到 18，并统一在 VSCode 和 Vim 中使用 clangd 语言服务器。
