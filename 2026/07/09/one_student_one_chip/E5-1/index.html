Verilator User’s Guide — Verilator 5.050 documentation

介绍

Verilator 包将 Verilog 和 SystemVerilog 硬件描述语言（HDL）设计转换为 C++ 或 SystemC 模型，编译后即可执行。Verilator 不是传统的模拟器，而是一个编译器。

Verilator 通常的使用方式如下：

  1. verilator 可执行文件的调用参数与 GCC 或其他仿真器（如 Cadence Verilog-XL/NC-Verilog 或 Synopsys VCS）类似。Verilator 读取指定的 SystemVerilog 代码，进行 lint 检查，可选地添加覆盖率和波形跟踪支持，并将设计编译成源级多线程 C++ 或 SystemC “模型”。生成的模型 C++ 或 SystemC 代码以 .cpp 和 .h 文件形式输出。这一过程称为“Verilating”，该操作称为“to Verilate”；输出结果称为“Verilated”模型。

    lint: 静态代码分析

  2. 仿真需要一个用户编写的小型 C++ 封装文件，即“wrapper”。该封装定义了 C++ 标准函数 main()，用于将 Verilated 模型实例化为 C++/SystemC 对象。
  3. 用户 C++ 封装文件、Verilator 生成的文件、Verilator 提供的“运行时库”，以及（如果适用）SystemC 库，随后通过 C++ 编译器编译，生成仿真可执行文件。
  4. 生成的可执行文件将在“仿真运行时”执行实际仿真。
  5. 如果适当启用，可执行文件还可以生成设计的波形轨迹以供查看。它还可以创建覆盖率分析数据用于后分析。

示例

示例1：

verilator --binary -j 0 -Wall our.v

  • --binary 告诉 verilator 去做所有的 生成 可执行的仿真文件的步骤
  • -j 0 有几个 cpu 调用 几个 cpu 线程
  • -Wall 更强的 lint 静态编码检查
  • our.v 我们的 SystemVerilog 文件

示例2：

verilator --cc --exe --build -j 0 -Wall sim_main.cpp our.v

  • --cc 以获得 cpp 输出
  • --exe 通过该参数并提供一个 sim_main.cpp 文件，构建系统的输出将不再只是一个库文件，而是一个可以直接运行的可执行文件。
  • --build 因此 Verilator 会自行调用 make。这样我们就不需要手动将 make 作为单独步骤来调用。
  • -j -Wall 同上
    *注意： –cc 和 –exe 仅仅是往 .mk 文件里面添加了 一些内容，如最终的编译目标。但是实际编译操作，生成最终的可执行文件仍然需要 –build。

    这个时候，可能对于 –binary 更会觉得奇怪，为什么 –binary 不需要 –build？

因为 –binary 隐含:

  • –cc（生成 C++ 模型）
  • 自动生成一个含 main() 的文件（相当于 Vour__main.cpp）
  • –exe（在 Makefile 中加入可执行文件目标）
  • –build（自动 make）
    * 不过 –binary 不可以自动接受 sim_main.cpp 参数

浏览 obj_dir 可以看到：

  • xxx.d 文件 是依赖关系文件，通常由编译器在编译中自动生成

  • xxx.a 文件 是归档文件(多个 .o 的压缩)，用作静态库

  • 观察 Vour__ALL.cpp 你可以发现这里面 只有include "xxx.cpp"（包含了这里全部的 cpp）。这样可以 仅仅 实例化一次（比如某个函数 多个cpp 都调用了，如果分开来 编译，那么 每一个 .o 都会包含一次这个函数的实例化。而合并起来最后仅仅编译 Vout__ALL.cpp 最后就仅仅回仅实例化一次）

  • 和第一次相比，最关键的就是

    • 多了 sim_main.d sim_main.o
    • 少了 Vour__main.cpp

  • 相比之下：

    • 第一种：verilator --binary -j 0 -Wall our.v
      • --binary = 直接生成可执行文件，不需要用户提供主函数。Verilator 会自动生成一个默认的 Vour__main.cpp，里面包含一个简单的 main()（通常只做时钟驱动和仿真完成检查），然后编译链接成可执行文件 Vour。
    • 第二种：verilator --cc --exe --build -j 0 -Wall sim_main.cpp our.v
      • --cc = 只生成 C++ 代码（不自动生成 main）。
      • --exe = 告知需要可执行文件（结合 --build 会编译链接）。
      • --build = 自动执行 make 构建。
      • 用户必须提供 sim_main.cpp，其中包含自定义的 main() 和测试逻辑。Verilator 不会生成 Vour__main.cpp，而是编译你的 sim_main.cpp。

为什么需要 自己 创建 sim_main.cpp ?

  • 自动生成的 Vour__main.cpp 不会主动给设计输入信号赋值。
  • 仿真不仅是运行，更重要的是验证结果是否正确。自动生成的 main 不做任何断言检查。
  • 调试硬件设计几乎 必须 看波形。自动生成的 main 没有波形输出。
  • 实际项目常用随机测试，这需要你自己控制随机种子和序列。
  • 还有复杂的时序交互、外部模型、性能统计等等…

Verilog的仿真行为和编码风格

verilog 标准手册比起综合，更偏向仿真

  1. 使用#0可以将赋值操作强制延迟到当前仿真时刻的末尾.
    • 不正确。#0 并不会将操作延迟到仿真时刻的末尾。在Verilog的事件队列中，#0 只是将赋值操作推迟到当前仿真时间的非活跃事件队列中执行。而在非活跃队列之后，还有非阻塞赋值（NBA）更新队列和监控（postponed）队列。因此 #0 之后执行时，可能依然无法获取到当前时刻非阻塞赋值的最终值。如果要想在仿真时刻的最后打印变量值，应使用 $strobe 或 $monitor。
  2. 在同一个begin-end语句块中对同一个变量进行多次非阻塞赋值, 结果是未定义的.
    • 不正确。在同一个 begin-end 顺序语句块中，非阻塞赋值语句会按顺序求值并调度到 NBA 队列。如果对同一变量多次赋值，最后一次赋值会覆盖之前的赋值，最终结果是有明确定义的（即最后一次赋的值），而不是未定义的。
  3. 用always块描述组合逻辑元件时, 不能使用非阻塞赋值.
    • 不正确。用 always 块描述组合逻辑时完全可以使用非阻塞赋值，且在语法和综合上是合法的。虽然业界最佳实践通常推荐组合逻辑使用阻塞赋值（=），时序逻辑使用非阻塞赋值（<=），但这并不意味着组合逻辑“不能”使用非阻塞赋值。只要逻辑完整（不产生意外的锁存器），使用非阻塞赋值依然可以实现正确的组合逻辑。
  4. 不能在多个always块中对同一个变量进行赋值.
    • 正确（此条描述是正确的，保留作为参照）。在多个 always 块对同一个变量进行赋值属于多驱动冲突。这会导致仿真行为不确定并在综合时报错。
  5. 不建议使用$display系统任务, 因为有时候它无法正确输出变量的值.
    • 不正确。$display 是 Verilog 中最基础且极其重要的调试系统任务。虽然它在当前仿真时刻的活跃区域执行时，可能打印不到此时即将在 NBA 区域更新的非阻塞赋值结果，但这并不意味着 display本身“无法正确输出”或“不建议使用”。针对非阻塞赋值的最终结果，正确的做法是改用‘display本身“无法正确输出”或“不建议使用”。针对非阻塞赋值的最终结果，正确的做法是改用‘strobe，而不是摒弃 $display`。
  6. $display无法输出非阻塞赋值语句的结果.
    • 不正确。$display 完全可以输出非阻塞赋值的结果。只要 $display 的执行时间点在该非阻塞赋值的更新事件之后（例如在下一个仿真时刻，或通过适当延迟后调用），就能正确打印出更新后的变量值。
  • 在 always 块里赋值 -> 声明为 **reg**。
  • 用 assign 在外面赋值 -> 声明为 **wire**。
  • 固定不变的常量 -> 声明为 **localparam**。

    但这并不最终综合后的，就是 reg

五种事件区域

  1. 激活事件(active event)区域 (R1) , 记为, 存放发生在当前仿真时刻, 且能被处理的事件.

    阻塞赋值一般会按顺序放在这里，注意 $display 也在这里

  2. 未激活事件(inactive event)区域 (R2) , 记为, 存放发生在当前仿真时刻, 但不能立即处理的事件, 需要在为空时, 才能处理这类事件.

    只有 #0 可以放入 R2

  3. 非阻塞赋值更新事件(nonblocking assign update event)区域 (R3) , 记为, 存放在之前的仿真时刻已经完成求值, 但需要在当前仿真时刻结束时才能进行赋值的事件, 需要在和均为空时, 才能处理这类事件.

    其实边沿触发器 是由两个 寄存器，一个在高电平使能，一个低电平使能，而两者直连，所以宏观开来，在边沿使得输出变化
    所以这个是因为寄存器的模型，一般都是在边沿，也即上一个电平的最后时刻才除法的更新，所以R3 在最后更新

  4. 监控事件(monitor event)区域 (R4) , 记为, 存放监控操作相关的事件, 需要在, 和均为空时, 才能处理这类事件.

    $strobe、$monitor 这一类

  5. 未来事件(future event)区域 (R5) , 记为, 存放在未来仿真时刻才处理的事件.

    #time 添加到其中

verilog 仿真器 其实只会执行 R1 区域的。R2\R3\R4\R5 只会在轮到他们的时候，放置在 R1 中。

阻塞赋值更新紧紧跟着 右侧表达式的计算
非阻塞赋值 是计算完成右侧表达式的数值后，放入更新队列（即计算别的表达式的时候 还是原来的数值）

工艺映射

工艺映射是指从工艺无关的电路表示映射到具体工艺的实现.

dfflibmap -liberty cell.lib 的流程就是：

  1. 读取 cell.lib，识别库里有哪些 DFF 类型。
  2. 建立“Yosys 内部 DFF → 库单元”的映射表。
  3. 扫描当前设计中的 DFF。
  4. 把能匹配的内部 DFF 替换成库里的真实单元。
  5. 当目标库没有某种专用 DFF 时，Yosys 会尝试用“库里已有的 DFF + 组合逻辑”实现

yosys> read_liberty -lib cell.lib

Verilog的RTL综合语义

综合层面 不允许 敏感事件列表中，同时出现 电平敏感和边沿敏感

1. 组合逻辑电路模型

组合逻辑应通过连续赋值、线网声明赋值或always语句来建模。

对于 组合逻辑电路的 always块，在敏感事件列表中，应该列出所有的作为输入参与运算或条件判断的变量，而且不应该有 上下沿。

如果 always(*)，那么 * 会被展开为 该 always 块中被读取（作为输入参与运算或条件判断）的变量。

一个 always 块要综合为组合电路时，不可以混用 blocking 和 nonblocking 语句

仿真或许可以，但是综合的时候，会报错或者不支持

2. 边缘敏感的时序逻辑电路模型

对于建模边沿敏感存储器件的变量，建议使用非阻塞过程赋值。

建议使用非阻塞赋值以避免Verilog仿真竞争条件。

对于在always语句内临时赋值和使用的变量，可以使用阻塞过程赋值。

一个 always 之能有 一个 敏感事件列表@

异步 set reset

在边沿敏感存储器件模型的敏感列表中，不允许出现电平敏感事件。

所以异步Async 只能是某个 信号的 edge，而不能在敏感事件中出现这个 信号的电平作为敏感事件

此外，always 块中必须包含一个 if 语句来描述第一个异步控制信号，并且可以使用嵌套的 else if 来描述额外的异步控制信号。最后必须有一个 else 语句，用来描述该 always 块的同步逻辑部分，这部分逻辑由未列在 if 和 else if 条件中的边沿控制变量（即时钟）来控制。

  • 对于每个异步控制，都有一个位于时钟分支之前的if语句。因此，异步置位和/或复位逻辑将具有比时钟边沿更高的优先级。其实只是一个优先级的问题，以便于可以实现异步控制。

3. 电平敏感存储器件建模

当以下所有条件均满足时，可为变量建立电平敏感存储器件模型：

  • 该变量在无边沿事件的always语句（组合逻辑建模风格）中被赋值。

4. 三态驱动器的建模

当变量被赋值为z时，应建模三态逻辑。z的赋值可以是条件性的或无条件的。如果信号的任何驱动源包含对值z的赋值，则所有驱动源都应包含这样的赋值。

z赋值不会在变量赋值间传播（包括隐式赋值，例如模块实例化中发生的赋值）。

5. 支持 x 或 z

  • 值x可用作赋值右侧的基本表达式，以表示综合的无关项。

    • 即这个输出在该条件下取 0 还是 1 都无所谓，综合器可以自行选择，以便简化电路。

  • 值x可用于casex语句中的case项表达式（可与其他表达式混合，如4’b01x0），以表示综合的无关值。

  • 值x不得与任何运算符一起使用，也不得与其他表达式混合。

    • 即 仅仅可以直接赋值 x ，而不可以 运算后赋值 x

  • 值z可用作赋值右侧的基本表达式，以推断三态驱动器。

  • 值z（或?）可用于casex和casez语句中的case项表达式（可与其他表达式混合，如4’bz1z0），以表示综合的无关项。

  • 值z不得与任何运算符一起使用，也不得与其他表达式混合。（三态倒是允许 ?: 的三目运算符）

6. ROM 建模

异步ROM应使用以下风格之一建模为组合逻辑：
a) 数据在case语句中的一维数组（见5.6.1）。
b) 数据在initial语句中的二维数组（见5.6.2）。(对于 ROM RAM，许多 FPGA 综合工具是支持 initial 的)
c) 数据在文本文件中的二维数组（见5.6.3）。
rom_block属性应用于标识建模ROM的变量。如果使用了logic_block属性，则意味着不应推断ROM，而应使用组合逻辑。
