配置选项

这是 GCC 在 Ubuntu 中编译时的配置参数，包括语言支持（C、C++、Fortran 等）、安装路径、多线程模型（posix）、多架构支持（m32/m64/mx32）、LTO 优化、offloading 等。

对于 -I

-I 的主要作用是：

  • 将指定目录加入头文件搜索路径，且在标准系统目录之前被搜索（见搜索顺序第3步）。
  • 因此，你可以用 -I 来覆盖系统头文件，即用自己的版本替换标准版本。
    ⚠️ 注意事项：不要用 -I 添加供应商提供的系统头文件目录，而应用 -isystem。因为 -I 的目录被视为普通用户目录，可能产生不必要的警告，且会干扰系统头文件的顺序。

其他选项（–iquote、–isystem、–idirafter）在搜索顺序中依次出现：

  1. **-iquote**：仅用于 #include "..." 形式，在 -I 之前搜索。
  2. **-isystem**：在 -I 之后、标准系统目录之前搜索，并将目录标记为系统头文件（抑制警告）。
  3. **-idirafter**：在标准系统目录之后搜索，也标记为系统目录。
    若某个目录同时被 -I 和 -isystem 指定，-I 会被忽略，该目录仍作为系统目录保留在原位。

编译

clang

描述

  • Driver(驱动): 控制并协调编译器、汇编器和链接器等底层工具执行的入口程序，用户通过它透明地使用这些工具。
  • Preprocessing(预处理): 处理源文件的词法分析、宏展开、头文件包含等预处理指令，输出 .i/.ii 等中间文件。
  • Parsing and Semantic Analysis(解析与语义分析): 将预处理后的记号解析为抽象语法树，并进行类型检查和语义分析，生成大部分编译警告和解析错误。
  • Code Generation and Optimization(代码生成与优化): 将抽象语法树转换为 LLVM IR 并优化，最终生成目标机器的汇编代码或直接生成目标文件。
  • Assembler(汇编): 将汇编代码转换为机器码，生成目标对象文件（.o 文件）。
  • Linker(链接): 将多个对象文件和库文件合并，解析符号引用，生成最终的可执行文件或动态库。
  • Clang Static Analyzer(Clang 静态分析器): 集成在 Clang 驱动中的代码静态分析工具，通过分析源代码自动检测潜在的程序缺陷。

option

  • -E(仅预处理): 只运行预处理阶段，处理宏展开和头文件包含，输出 .i/.ii 中间文件。
  • -fsyntax-only(仅语法检查): 运行预处理、解析和类型检查阶段，输出抽象语法树但不生成代码。
  • -S(生成汇编): 运行上述所有阶段加上 LLVM 生成、优化和目标代码生成，输出汇编文件（.s）。
  • -c(编译为目标文件): 运行上述所有阶段加上汇编器，生成目标对象文件（.o）。
  • no stage selection option(无阶段选择选项): 若未指定阶段选择选项，则运行上述所有阶段，并启动链接器将结果合并为可执行文件或共享库。

clang -fsyntax-only -Xclang -dump-tokens a.c

- -Xclang 是一个透传选项，作用是将紧随其后的一个参数直接传递给 Clang 的编译前端

中间代码生成

中间代码 是 由编译器定义的，面向编译场景的 ISA（Instruction Set Architecture 指令集架构），也称中间表示(Intermediate Representation, IR)或中间语言(Intermediate Language)

编译的工作主要是将C程序的状态机翻译成ISA的状态机, 也即, 将C程序的变量翻译成寄存器或内存, 将C程序的语句翻译成指令序列.

中间代码还能作为多种源语言(如C语言, Fortran, Haskell等) 和多种目标语言(如x86, ARM, RISC-V等)之间的桥梁

不同的编译器可能会采用不同的中间代码, 例如clang使用的中间代码叫LLVM IR, gcc使用的中间代码叫GIMPLE. 不过, 我们并不需要理解中间代码的具体细节, 只需要从状态机模型的视角大致了解中间代码生成的工作过程即可.

编译器优化

对于编译优化的要求，满足程序可观测行为的一致性：

  • 对于 volatile 修饰的要严格执行（按照 C 语言逐行执行，不允许优化）
  • 程序结束时, 写入文件的数据需要与严格执行时一致
  • 交互式设备的输入输出(stdio.h)需要与严格执行时一致

对于 a=f(); a=10 中 f能否优化掉

  • 取决于 编译器是否知晓 f() 有无副作用
  • 如果 编译器把握不住，默认当有副作用，不优化
  • 如果编译器可以看到完整定义，或被告知不会有副作用，则可以优化
  • static 表示的是内部链接（internal linkage）：”只有当前这个 .c 文件（翻译单元）能看到 f 和 g，其他文件看不到。”
  • 它不是说 f 变成了局部变量，也不意味着 f 的返回值有什么特殊限制。static 函数和普通函数在调用方式、返回值传递上没有任何区别。

static：

  1. 修饰局部变量（C/C++）
    定义为静态局部变量。存储在静态数据区（全局区），生命周期延长至整个程序运行期；仅在首次执行到该定义时初始化一次（未显式初始化则自动为 0）；作用域仍限于所在代码块（函数/块）内。
  2. 修饰全局变量（C/C++）
    将变量的链接属性改为内部链接（internal linkage），即该变量仅在当前翻译单元（源文件）内可见，其他文件即使使用 extern 也无法引用。
  3. 修饰普通函数（C/C++）
    与修饰全局变量类似，函数仅在当前翻译单元内可见，对其他源文件隐藏，防止跨文件的命名冲突。
  4. 修饰类的成员变量（仅 C++）
    声明为静态数据成员。属于类本身而非某个对象，所有实例共享同一份拷贝。必须在类外定义和初始化（C++17 前；C++17 起可用 inline static 在类内初始化）。
  5. 修饰类的成员函数（仅 C++）
    声明为静态成员函数。属于类，不依赖于对象实例，没有 this 指针；只能访问静态成员；可通过 ClassName::func() 直接调用。
  6. C++11 线程安全局部静态（Magic Statics）
    C++11 起，函数内的 static 局部变量由编译器保证线程安全——首次调用时初始化，后续调用直接跳过初始化，无需手动加锁。

__attribute__((const)) 的真实含义：表示函数不读取任何全局内存，其返回值仅依赖于参数，且没有任何副作用。
所以编译器看到这种参数就敢大胆优化

汇编

汇编语言是指令的符号化表示。但是电路无法处理文本，所以需要将 汇编语言 转换为对应的 二进制编码。
这个步骤称之为汇编，完成的工具称之为汇编器

不过对比还是可以看到很多 .xxx, .Lxxx。

  • .xxx:这些叫做 汇编器的伪指令，不是给 cpu 的，是给 汇编器看的。告诉汇编器哪段代码应该放到哪里，符号是全局还是局部，对齐等等。
  • .Lxxx: 这类以 .L 开头的标签是局部标签（Local Labels）。它们只在当前 .s 文件内部当”书签”用（比如计算函数大小、跳转目标）。不会进入最终 ELF 的符号表，别的文件看不到。

一个典型的越界

应用程序二进制接口（ABI, Application Binary Interface）

是 程序、编译器、操作系统、库函数、ISA 之间的 约定和规范，称作 ABI

C 语言标准 由于要兼容各种计算机系统，所以标准无法定太死。但是对于具体的 计算机系统，很多行为就可以确定下来了。而 ABI 作为 该 计算机系统 在二进制层次的约定，它可以看作是 C 语言标准的一种具体实现，所以很多 实现定义行为 也会写入 ABI。

ABI作为一种规范, 其内容包括:

  • 处理器的指令集, 寄存器结构, 栈的组织, 访存类型等
  • 处理器可直接访问的基本数据类型的大小, 布局, 对齐方式
  • 调用约定, 用于规定函数的参数如何传递, 返回值如何获取
  • 应用程序如何向操作系统发起系统调用
  • 目标文件的格式, 支持的运行库等

  • 在 JALR 中 R[rd] = PC + 4 需要放在最后，不能放在 PC 之前

ebreak

“2.8. Environment Call and Breakpoints” (“The RISC-V Instruction Set Manual Volume I: Unprivileged Architecture”, p. 34)

“The EBREAK instruction is used to return control to a debugging environment.

ECALL and EBREAK were previously named SCALL and SBREAK. The instructions have the same functionality and encoding, but were renamed to reflect that they can be used more generally than to call a supervisor-level operating system or debugger.

EBREAK was primarily designed to be used by a debugger to cause execution to stop and fall back into the debugger. EBREAK is also used by the standard gcc compiler to mark code paths that should not be executed.

Another use of EBREAK is to support “semihosting”, where the execution environment includes a debugger that can provide services over an alternate system call interface built around the EBREAK instruction. Because the RISC-V base ISAs do not provide more than one EBREAK instruction, RISC-V semihosting uses a special sequence of instructions to distinguish a semihosting EBREAK from a debugger inserted EBREAK.” (“The RISC-V Instruction Set Manual Volume I: Unprivileged Architecture”, p. 35)

EBREAK指令用于将控制权返回给调试环境。

ECALL和EBREAK先前分别命名为SCALL和SBREAK。这些指令具有相同的功能和编码，但已重新命名以反映它们可以更广泛地使用，而不仅仅是调用监督级操作系统或调试器。

EBREAK主要设计用于调试器，以使执行停止并回退到调试器。EBREAK也被标准gcc编译器用于标记不应执行的代码路径。

EBREAK的另一个用途是支持“半主机”（semihosting），其中执行环境包含一个调试器，该调试器可以通过围绕EBREAK指令构建的替代系统调用接口提供服务。由于RISC-V基础ISA仅提供一条EBREAK指令，RISC-V半主机使用一条特殊的指令序列来区分半主机EBREAK与调试器插入的EBREAK。

体验显示功能

  • 函数体
    • 函数体其实就是按照 帧率 推测单帧的持续时间，到达就刷新，并统计当前 1s 刷新了几帧
    • 然后 时间经过 1s 后，打印当前帧率，清零统计数据
  • p函数
    • Time Stamp Counter（时间戳计数器）
    • 这个其实就是一个根据 tsc 更新当前颜色的小函数，没什么特殊之处，*6 *7大概也是随便写的
  • update 函数
    • 该函数主体其实就是螺旋画颜色
    • 不断的螺旋，使用 p(tsc+step) 更新颜色到当前方格，标记使用过，不断切换方向，直至绘制完新的一帧
  • redraw 函数
    • 在获得 update 的画布数据后，通过 redraw 绘制到屏幕
    • io_read 读取当前屏幕尺寸，计算绘制像素 长 宽
    • 循环绘制每个像素点的对应颜色
    • io_write 写入到屏幕

      * 你应该还会注意到，这里有一个断言。这个断言你或许会觉得很奇怪，放着干吗用？拖一下屏幕，不久可能像素变多，然后出问题吗？
      然后你拖动了一下，发现拖不动…
