输入输出

设备与CPU

  • 访问设备 = 读出数据 + 写入数据 + 控制状态
  • 而控制状态本质上也是读写设备寄存器的操作，所以访问设备 = 读/写操作

端口 I/O

端口I/O是CPU通过独立的地址空间和专用指令（如in/out），直接与硬件设备寄存器进行数据交换的底层通信机制。

端口映射I/O所能访问的I/O地址空间的大小, 在设计I/O指令的那一刻就已经决定下来了

内存映射 I/O

内存映射I/O是将硬件设备的寄存器直接映射到CPU的内存地址空间，使CPU使用普通的内存读写指令（而非专用指令）即可访问和控制外部设备。

物理内存的地址空间和CPU的位宽都会不断增长, 内存映射I/O从来不需要担心I/O地址空间耗尽的问题.

  1. MMIO 位于物理地址空间，归属内核态管理。用户态程序想要操控硬件，必须通过陷阱（系统调用）陷入内核交由驱动处理（除非内核通过特殊机制如 mmap 显式下放了权限）。
  2. 用户态通过 fd 这一统一逻辑接口发起 I/O 请求，触发系统调用（Trap）陷入内核；内核驱动接管后，通过 MMIO/PMIO 操作硬件寄存器下达指令，最终由 DMA 负责在内存与硬件之间直接搬运庞大的业务数据。

NEMU 中的输入输出

  • nemu/include/device/map.h

  • 在结构体中，会记录：

    • [Guest视角] 客户机物理地址的起始位置
    • [Guest视角] 客户机物理地址的结束位置
    • [Host视角] 宿主机分配的真实内存起始地址（用来冒充硬件寄存器）
    • 驱动回调函数（模拟硬件读写时的真实副作用，如打印字符或更新状态）

  • nemu/include/memory/vaddr.h

nemu/src/device/io/map.c

  • new_space: new_space 是一个极简的**“向上取整页对齐”的线性内存分配器（Bump Allocator）。
  • check_bound: 校验 CPU 访问的物理地址是否落在指定设备的合法映射区间 [low, high] 内，越界或未映射则触发断言报错并打印引发错误的 PC 指针。
  • invoke_callback: 是一个安全调用回调函数的包装器（Wrapper）。由驱动提供。
  • init_map() : 初始化 I/O 空间：申请一块最大 32MB 的内存池，并将分配指针指向起始位置。纯粹是为了软件仿真（模拟）而设计的（因为实际上这里早给映射到实际的硬件寄存器去了）。
  • map_read() : 处理读请求：校验边界并计算偏移量后，先触发读回调（准备数据），再从映射的宿主内存中读取指定长度的数据返回。
  • map_write() : 处理写请求：校验边界并计算偏移量后，先将数据写入映射的宿主内存，再触发写回调（模拟硬件接收动作）。

理解 mainargs

RISC-V (NEMU) 平台：二进制注入机制
在 abstract-machine/am/src/riscv/npc/trm.c 中，mainargs 被定义为一个静态常量数组：

结合 abstract-machine/scripts/platform/nemu.mk 中的构建规则：

实现原理：
编译阶段，使用预设的占位符字符串替换 mainargs 的实际内容。在 insert-arg 阶段，Python 脚本读取二进制文件，定位该占位符的位置，并使用用户指定的 mainargs 进行覆盖。

边界容错机制：
若未传入 mainargs（长度为 0），Python 脚本将使用 64 字节的 \0 进行填充。在 C 语言底层视角下，这构成一个合法的空字符串，从而跳过输出逻辑。此机制确保了无参数场景下的安全性，属于框架的显式容错设计。

Native 平台：环境变量传递机制
在 native 平台中，native.mk 未包含任何关于 mainargs 的显式处理逻辑，既未作为 argv 传递，也未在 Makefile 中显式声明。为定位其传递链路，使用全局搜索：

搜索结果显示，在 ./am/src/native/platform.c:174 中存在如下代码：

实现原理：
native 平台运行于 Linux 用户态，直接利用操作系统的环境变量机制。执行 make ARCH=native run mainargs=I-love-PA 时，Make 工具将 mainargs=I-love-PA 注入为子进程的环境变量。程序启动后，platform.c 通过 getenv 函数读取该环境变量，并将其作为参数传递给 main 函数。整个过程无需修改二进制文件。

机制对比总结
同一套上层接口 main(const char *args)，在不同平台下的底层实现存在根本性差异：

  • NEMU 平台：运行于无操作系统的裸机环境，通过编译期占位符与运行前的二进制注入（insert-arg.py）实现参数传递。
  • Native 平台：运行于 Linux 用户态，依赖操作系统提供的环境变量机制（getenv）实现参数传递。

bump allocator

在这里先找到堆的起始

RETURN VALUE
The malloc() and calloc() functions return a pointer to the allocated memory, which is suit‐
ably aligned for any built-in type. On error, these functions return NULL. NULL may also be
returned by a successful call to malloc() with a size of zero, or by a successful call to
calloc() with nmemb or size equal to zero.

malloc() 和 calloc() 函数返回一个指向已分配内存的指针，该指针已进行适当对齐，可用于任何内置类型。出错时，这些函数返回 NULL。另外，如果成功调用 malloc() 时 size 为 0，或者成功调用 calloc() 时 nmemb 或 size 等于 0，这些函数也可能返回 NULL。

[!tips] 适当对齐
“适当对齐（Suitably aligned）”是一个硬件层面的硬性要求。简单来说，它的意思是：你 malloc 返回的指针地址，必须是某个特定字节数（通常是 8 字节或 16 字节）的整数倍。

  • C 标准的规定：必须满足 max_align_t 类型的对齐要求。在大多数架构上，这通常是 long double 或 uint64_t 的大小。
  • 在 32 位 RISC-V (NEMU) 上：虽然基础字长是 32 位（4字节），但由于你需要支持 64 位整数（uint64_t）和双精度浮点数（double），为了兼容这些 8 字节数据类型，最安全的做法是强制 8 字节对齐。
  • 在 NEMU 的 RISC-V 内存模型中，地址是按字节编址的：一个地址对应一个字节，也就是 8 bit。

所以综上，进行了8Byte对齐。

          2. 如果超出下界，放到最底下位置，标记 miss，标记消失倒计帧数
  4. 渲染函数
    1. 先将原来已经绘制的用 blank 覆盖
    2. 再将新的字符进行绘制，并存入static x数组（用于下一帧的清除）
  5. 点击判定
    1. 匹配按键和最下方的字母，如果有就 hit++并速度取反，颜色变绿，否则错误就wrong++
